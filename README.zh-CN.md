# dsh-hillstone-cli-ops

一个 [DeepSeek Harness](https://github.com/deepseek-ai)（DSH）插件，把 Hillstone / StoneOS
网络设备搬进 DSH 的右侧栏：管理设备、打开一个真实的 SSH 终端、查看每次连接的审计日志、
写下助手不许打破的命令规则，同时给助手注册 9 个工具，让它自己就能做这些事。

[English README](README.md)

本插件由两半组成：Node 宿主半边（SSH、加密、会话日志、agent 工具）和浏览器客户端半边
（右侧栏标签页 + xterm.js 终端）。两半都由同一份 `src/` 源码构建。

---

## 你得到什么

**右侧栏的一个「设备运维」标签页**，内含四个子标签：

| 子标签 | 做什么 |
| --- | --- |
| **设备管理** | 设备的增删改查（名称 / IP / 账号 / 密码 / SSH 端口 / 设备类型 / Web 端口 / 备注）。新增、复制、编辑都走同一个**居中于窗口**的弹窗（与 DSH 自带弹窗一致），背景可点、Esc 可关。卡片名称那一行右侧是两条登录入口：**CLI 登录**（SSH 终端）与 **WebUI 登录**（浏览器）。名称前面有一盏状态灯，显示最近一次的存活检测结果：绿=端口可达、红=不可达，首次启动、还没检测过则不显示。 |
| **终端** | 每条活动连接对应一个 xterm.js 终端。输入发给宿主，设备输出经 SSE 流回面板。新连接出现时面板直接切到「终端」，你落在实时会话上，而不是设备列表。 |
| **日志** | 每次连接的审计记录：谁连了哪台设备、输入了什么、执行了哪些命令、会话何时因何结束。 |
| **执行策略** | **由你**书写的规则：一个每天循环的时间窗口，绑定你自己填写的命令模式。当 agent 下发的命令落在窗口内又命中模式时，宿主在任何 SSH 流量发生之前拒绝它，并记录原因。完整语义见 [docs/执行策略.md](docs/执行策略.md)。 |

**9 个 agent 工具**，让助手不必等你也能操作设备：

`hillstone_list_devices`、`hillstone_open_terminal`、`hillstone_send_input`、
`hillstone_get_output`、`hillstone_close_terminal`、`hillstone_list_sessions`、
`hillstone_run_and_analyze`、`hillstone_scan_liveness`、`hillstone_web_login`。

`hillstone_run_and_analyze` 批量执行命令，把输出连同一句自然语言目标（「检查接口状态和 CPU
负载」）交给宿主 LLM 分析。默认复用运维人员已经打开的终端会话，因此你可以在标签页里看着
agent 干活；没有活动会话时它会退回到一次性 exec 通道。

`hillstone_scan_liveness` 把每台设备的 TCP 可达性当作数据返回——与状态灯用的是同一套探测，
因此助手不必去读面板就能分辨「设备离线」和「端口不可达」。`hillstone_web_login` 驱动设备的
管理界面登录并返回结论（ready / captcha / error），遇到验证码时把窗口留给人工完成。

### WebUI 登录

每张设备卡片的名称行上都有 **WebUI 登录** 按钮，和 **CLI 登录** 并排。它会在一个真实浏览器窗口里打开设备的管理界面，
用该设备已保存的账号登录，然后把窗口留在你的桌面上——之后你就在浏览器里自己操作。

```
https://<设备 IP>:<Web 端口，未填则 443>/
```

用之前有三件事值得知道：

- **密码不会到达面板。** 宿主解密后直接填进表单，只回传一个结论——已登录 / 需人工完成 / 失败。
  本插件的浏览器半边根本看不到密码。
- **它只尝试一次，这是有意为之。** 密码错一次之后设备就会开始要求图形验证码，而一旦开始要求，
  之后任何自动尝试都不可能成功。所以失败被报为「需人工完成」并把窗口留着让你手工完成，而不是
  重试到锁死。
- **浏览器 profile 是持久的**（`<数据目录>/webui/<设备 id>`），所以对同一台设备第二次点击通常直接
  打开已登录的会话，不再碰密码。

这个按钮会在运行 DSH 的那台机器上启动一个**有界面**的 Chromium——它不是无头检查，运行期间会
占用一部分屏幕。

浏览器用的是 Playwright 自带的 Chromium。`pnpm install` 会把 Playwright 钉在一个其浏览器版本与
普通桌面环境已缓存内容相匹配的版本上，因此不需要额外下载；如果你升级了 Playwright 而它要求新
浏览器，执行一次 `npx playwright install chromium` 即可。

## 安装

```bash
git clone https://github.com/jazhu/dsh-hillstone-cli-ops
cd dsh-hillstone-cli-ops
pnpm install
pnpm run build          # 重新生成 dist/（不入库）
```

然后把 DSH 指向这个目录——既可以在插件管理器里作为本地 bundle，也可以把包装进你的 profile：

```bash
pnpm pack && <你的 dsh 插件安装命令> ./dsh-hillstone-cli-ops-1.0.0.tgz
```

**装完请重启 DSH 主进程。** 停用再启用插件不会重建运行中进程的宿主 fiber，所以新的宿主代码
（SSH 处理、工具、日志写入）只有在真正重启后才生效。

环境要求：Node 22+；一个暴露了 `tools`、`slots`、`sidebarRightTabs`、`sidebarRight`、
`uiWorkspace` 这些服务的 DSH 版本；以及 `ssh2` / `xterm`（由 `pnpm install` 装好）。

`package.json` 在 `dsh.client.inject` 里列出客户端需要的服务，这个列表是有约束力的：它正是
loader 在任何代码运行之前读取的东西。客户端半边自己的 `export const inject` 与这份 manifest 是
**同一个事实的两个独立陈述**，所以 `test/bundle-gate.mjs` 会比对它们，一旦漂移就让门禁失败。
你新增服务时记得两处一起改。

## 设计说明

这里有若干决定是**从实测中得来的**，而不是从显而易见的猜测。

### StoneOS 上的分页器不是可选项

在真实的 SG-6000 上实测：`show cpu detail` 产生 9172 个字符，在 ` --More-- \0` 处**停了 13 次**，
而设备**不输出任何 SGR 颜色序列**。

真正咬人的是第二点：**分页器会吞掉任何输入的东西。** 在分页器等待期间发送的命令会被静默吞掉——
分页器只是把本页剩余内容刷完然后回到提示符。于是「写入命令然后等提示符」的工具会一直挂到超时，
而那条命令**从未被执行**。

因此 `hillstone_run_and_analyze` 会监测 `--More--` 并用一个空格应答它（走与其他输入同一条写队列），
同时报告它翻了多少页。`hillstone_send_input` 会自动提交一条裸命令（见下文），这样模型不必记住
那个结尾的回车。

连接时我们**不**发送 `terminal length 0`。SG-6000 会以 `^-----unrecognized keyword` 拒绝它并且照样
分页，所以它除了在每个会话顶部放一条假设备错误之外，什么也没换来。

### 只登录一次，因为第二次不可能成功

设备的登录接口在密码错误时不仅返回一个错误，还会**开始要求图形验证码**。这个验证码不是会自行
解除的软锁定——从那一刻起它就长在表单上，而且接口对正确密码也不豁免它。于是会自动重试的登录
第二次必然失败，而且看起来像是「密码不对」，真相却是「第一次错了，现在需要一个人」。

所以登录只跑一次，结论从 `POST /rest/login` 的响应体读出（`{"success":true…}`，或者
`exception.message` 加上验证码要求），然后把窗口交出去。面板把这一档标为**需人工完成**而不是
失败，因为验证码是等着人来做的事，不是故障。

同一份实测还带来两个较小的决定：结论取自响应体而不是刮页面，因为登录后的页面上有几百个毫不相干
的表单元素；以及 Playwright 用**动态 `import()`** 加载，这样装不上时只让一次按钮点击失败并给出
可读的错误信息，而不是在加载期把整个宿主插件拖垮。

### `send_input` 会提交，但知道什么时候不该

「模型传一条裸命令然后等输出」是压倒性的常见情况，没有 `\r` 的话文本就只是躺在设备的行缓冲里。
所以 `hillstone_send_input` 会补一个回车——除非这段输入明显不是一条命令行：

| `data` | 行为 |
| --- | --- |
| 多字符、不含控制字符、不为空白 | **补 `\r`** |
| 单个按键（翻页的 `" "`、退出的 `"q"`）或任何含控制字符的内容 | **原样发送** |
| 任何内容，但显式给了 `submit: true / false` | 显式值优先 |

`submit` 也接受字符串 `"true"` / `"false"`，因为一个偏 JSON 的调用方可能递过来字符串，而
`submit: "false"` 不能被当成真值。

### 输出游标按字节计

`hillstone_get_output` 是 `hillstone_send_input` 的读取半边：agent 用 `since` 游标轮询，而不是
重读全部内容或盲目 sleep。这个游标是**字节**偏移，不是字符偏移。输出记录有上限并在溢出时被重新
切片，所以字符串下标会在轮询的 agent 脚下发生位移；落在多字节字符中间的游标会被回退到首字节，
而不是吐出一个替换字符。判定「游标太旧」的条件是 `since < dropped`——与一个不断增长的总长相比，
会让任何新输出一到就看起来所有游标都过期了。

### 执行策略约束的是 agent，不是运维人员本人

网络设备上有一些命令，你绝不希望它在凌晨三点被执行——而下命令的正是助手。所以「执行策略」
让你自己写这条规则：一个**每天循环的时间窗口**（留空=始终生效，`22:00`–`06:00` 可跨午夜），
绑定**你自己填写的命令模式**。没有内置黑名单，宿主从不替你决定什么算危险。

匹配是**词边界包含、大小写不敏感**。模式 `reload` 能命中 `reload`、`reload force`、
`RELOAD now`，但不会命中 `reloading` 或 `firereload`。前缀匹配会过度拦截；正则则要求每个
运维人员都去学一种语法。这是在「够用」与「不误伤」之间的取舍，而边界本身是 Unicode 感知的
（`\p{L}` / `\p{N}`），所以在中日韩文本周围表现一致。

有两个决定值得直说：

- **只拦 agent 的入口。** `hillstone_run_and_analyze` 与 `hillstone_send_input` 在任何 SSH
  流量之前检查策略，返回带策略名的 `blocked` 结论；而人类那条 `/conn/input` 路径——你，在
  「终端」页里手敲——**刻意不检查**。一条连作者本人都绕不过去的规则，就是一条把作者自己锁在
  设备外面的规则；策略约束的是自动化，而不是写规则的那个人。
- **拒绝会留痕，且对设备零影响。** 拦截会写一条 `console.warn` 和一条带策略名与命中模式的
  会话日志 `event`。任何东西都不会到达设备，因此没有「执行了一半」的状态需要收拾。

拦截点位于 `runCommandVisible`（工具与 `/analyze` HTTP 路由共用）内部，以及
`hillstone_send_input.execute` 的顶部——所以只有一处检查，而不是每个调用点各写一遍。策略
落在 `policies.json`，与 `devices.json` 同目录、同一加密密钥，经既有的带 token 的回环 API
暴露 `GET/POST/PUT/DELETE /ops-api/policies`。

### 违反契约的 ToolDefinition 不会抛错

DSH 的 `ToolDefinition` 要求 `output.schema` 与 `output.render(args, value)`，并要求
`parameters` 是一张**扁平属性表**（`字段 → { type, description, required? }`），而不是一个
JSON Schema 对象。违反它不会在注册时报错——工具只是**永远不出现在 `Tool.listTools` 里**。
插件看起来一切正常，agent 却报告自己没法操作设备，日志里也没有任何一句说明原因。

所以回归套件和 bundle 门禁断言的是**契约本身**，不只是工具名：每个工具都必须有 description、
一张扁平参数表、一个 `execute`，以及一个能把真实结果渲染成可读文本块的 `output.render`，
并且渲染失败时是给出可读文本而不是抛异常。

### 密码永远不到达浏览器

设备密码用每个 profile 各自的密钥静态加密，只在宿主进程内解密。复制按钮是**服务端**的：宿主
复制的是**密文**，所以复制一台设备绝不会把明文密码搬进页面；编辑副本时密码框留空即保留继承来的
那个。

按「复制」**不会**创建任何东西。它打开的是用源设备预填好的**新增**弹窗，只有按「保存」才写入
记录——所以「取消」真的是取消，而不是留下一条没人要的 `-副本`。表单是以覆盖项的形式发给宿主的，
所以一个改过地址、账号或设备类型的副本，会严格按运维人员输入的内容创建，而他们没动的每个字段
仍然来自源设备（密码框留空意为「继承」，不是「置空」）。

### 侧边栏属于会话，而不是属于应用

连接建立时，插件会打开自己的右侧栏标签页。陷阱在于 DSH 的右栏是**按会话**的：每一次
`openTab` / `toggleExpanded` / `close` 都会经过 `sessions.onScreen` 解析，所以它总是落在用户
**当前正在看的那个对话**上。agent 在你读**另一个**对话时去连一台设备，过去就会把终端弹到那里。

于是每条连接都带上「是谁发起的」这个身份——宿主侧的 `originSessionId`，取自工具的
`exec.agent.id` 或由页面发送——并把展开动作路由到那个会话：先试会话内的 `openTabIn`（它不会把
你挪走），只有当那个会话从未有过右栏时，才用 `uiWorkspace.openSession` 把主栏切过去并在那边打开
标签页。这个切换是通过订阅发布屏幕会话的，所以 `openTab` 必须等到下一个 tick——同一个 tick 里
做会重新制造出正在修的那个 bug。而重复打开一个已存在的标签页只会聚焦它、不会展开右栏，因此
还有 `isExpanded()` / `toggleExpanded()` 的兜底。

### 弹窗居中，但遮罩保持克制

三个弹窗（新增设备 / 新增策略 / 会话明细）都**居中于整个窗口**，与 DSH 自带的告警中心设置弹窗
一致。这一点改过一次：早期版本把弹窗贴在右栏边缘，当时的理由是「不打断阅读」。实测下来那更像
一块侧栏浮层，而不是一个对话框——而且你的视线要横跨整屏才能找到它。

但**遮罩仍然不接管**。背景没有 `backdrop-filter` 模糊、没有压暗，点一下就能关掉，Esc 同样有效。
居中只回答「弹窗在哪」，不等于「必须先处理弹窗」。这两个决定要分开做，否则一个「更醒目」很容易
滑向一个「更强势」——m03636 定的拒绝 blur / 接管 / 必须点确认，至今仍然有效。

这件事还有一个只有截图才会暴露的推论：弹窗挂在 `<body>` 上、以**窗口**为中心，而面板本身只有
440px 宽。在 440px 的视口里「居中」和「撑满」是同一张图，所以文档里那三张弹窗图是按
**1280px 整窗宽度**拍的，`docs/assets/` 里另外四张才是 440px 的右栏宽度。理由记在
`docs/assets/README.txt` 里。

### 连接落在「终端」上，而不是「设备管理」上

打开面板只完成一半工作。标签页的 body 是由侧栏挂载的，所以如果在标签页还关着的时候察觉到连接，
就**没有人在听**——那个通知掉进了空处，面板带着设备列表出现，而那恰恰是唯一一个完全说明不了
「agent 现在在设备上干什么」的视图。

所以「显示终端」这个意图是在**打开标签页之前**被 park 住的，以它所属的会话为键，由 body 在挂载
时认领。这个顺序的两半都重要。先 park 覆盖的是「`openTab` 同步挂载 body」的情形；先问覆盖的是
「标签页从来没打开过」的情形，而 m04040 意味着应答的那个 body 可能是**另一个对话的**、晚一个
tick 才到。

早期版本 park 的是单个布尔值。在常见情形下（一个会话、一个面板）它看着是对的，但它会被「恰好
先挂载的那个面板」认领走——这就是同一个错会话 bug 低一层的重现。按会话分桶的 map 才让它不再
回来。

### 标签页对自己的描述

右栏会在任何人打开一个标签页之前展示它的 `guide` 条目，所以那段文字是本插件对一个从没见过这个
面板的用户所做的描述。它漂移了很久——在面板已经长出搜索、分页、存活探测、审计日志和上面那个
自动跳页之后，它还在只宣传「设备管理与 SSH 终端」。过期的说明比没有说明更糟：没有任何迹象提示
你即将打开的东西和标签写的不一样。

有两件事让它保持诚实。文案现在与面板一致，并且门禁会断言它，所以删掉这段描述会让构建失败。
那条断言在匹配前会先解码产物里的 `\uXXXX` 转义——esbuild 以 `charset: ascii` 产出，把转义手工
抄进正则曾经做出了一条会漏掉产物里已经存在的字符串的检查。

### 固定端口上的本地 API

浏览器半边无法直接调用宿主的服务，所以宿主开了一个回环 HTTP 服务（`127.0.0.1:18783`，
前缀 `/ops-api`）。它由一个按会话生成的 bearer token 守护，页面从 `GET /ops-api/_session` 取这个
token，而该端点只回应来自回环、且没有 `Origin` 或 `Origin` 是本地的请求——否则用户在使用
harness 期间访问的任何一个网页都能够到这个 API。页面在 `X-Ops-Token` 里携带该 token。

### 每次连接、每天一个日志文件

每次连接会写 `<dataDir>/oplog/<YYYY-MM-DD>/<connId>.jsonl`：一行头、每条
`input` / `command` / `event` 一行、以及最后一行记录结束原因。**没有结束行意味着会话仍在活动**
——只记录成功的日志不叫审计记录，所以日志在 SSH 握手**之前**就打开了，端口被拒或密码错误同样
会被记录。设备输出被**刻意**不记录：一次 `show tech-support` 转储会让日志膨胀三个数量级，而
设备自己留有日志。日期按本地时间分键，保留 30 天。

## 开发

```bash
node node_modules/typescript/bin/tsc --noEmit   # 类型检查（build.mjs 不以此为门禁）
node build.mjs                                  # esbuild 双产物构建
node test/terminal-regression.mjs               # 离线端到端
node test/bundle-gate.mjs                       # 对构建产物做特征断言
```

请按这个顺序运行。`bundle-gate` 断言的是 `dist/`，所以一次失败的构建否则会让它在**上一次的
产物**上照样通过——它会比较 `dist/*` 与 `src/**` + `build.mjs` 的 mtime，并报
`MISS … (STALE)`。

`test/terminal-regression.mjs` 会拿真实的 `dist/index.mjs` 对上一个自建的假 StoneOS（走真实
`ssh2`），其中包含一个会在 ` --More--` 处停下、并**吞掉**在那里输入的任何东西的假分页器——
与真机相同的失效模式。它只 apply 一次插件，并从**同一个**实例上捕获工具注册表——那个实例同时
提供 HTTP API，这正是生产环境的形态：DSH 只调 `apply` 一次，`activate` 内部让回环服务与
agent 工具共享同一份 store。若为工具另起一个实例，工具拿到的就会是**另一份**内存 store，
经 HTTP 建的规则会被静默地永远送不到它们手里。

`test/negctl-guide.mjs` 不在上面这条链里——它是对门禁本身的自检。它会把
`dist/client.js` 里某一条已发布的字符串替换掉，确认门禁里对应那条断言翻成 `MISS`，然后把
文件按字节原样还原。一条无法被证明会失败的断言不是覆盖率，只是装饰。

### 截图

[`docs/插件介绍.html`](docs/插件介绍.html) 里的面板图不是手绘稿。`tools/shots/capture.mjs`
把真实的 `dist/client.js` 放进 Chromium，按面板实际所在的右栏宽度渲染，宿主是真实的
`dist/index.mjs`，设备端是回归套件用的同一台假 StoneOS，fixture 走真实 `/ops-api` 灌进去。
UI 一改，手绘的 HTML 就会漂——标签引导文案（m06703）正是因此才被门禁钉住。

```bash
node tools/shots/capture.mjs        # 写出 docs/assets/*.png
node tools/shots/check-page.mjs     # 标签配平、每个素材都存在且被引用
```

`tools/shots/` 用 **npm** 装自己的 `react` + `react-dom`（UMD，供页面使用），不是 pnpm：
仓库根有 `pnpm-workspace.yaml`，pnpm 会把嵌套目录判为不合格的 workspace 子包，
然后**静默地什么都不装**。宿主在运行时提供 react，所以插件本身把它 external 掉了；
只有这个工装需要在磁盘上真的有一份。
