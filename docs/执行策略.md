# 执行策略（Execution Policy）

> 设备运维插件自 v1.x 起提供的「执行策略」能力：由运维人员**自行定义**的命令限制规则，而非主机侧内置的硬编码拒绝名单。

---

## 1. 它解决什么问题

Agent 可以调用 `hillstone_run_and_analyze` / `hillstone_send_input` 在真实设备上执行 CLI 命令。
为了避免 agent（或被其驱动的自动化流程）在不当的时间、对不该碰的命令动手脚，**运维人员可以预先写下规则**：

- 在**某个时间段**（例如夜间 22:00–06:00）内；
- 当命令命中**自己填写的命令模式**（例如 `reload`、`delete`）时；
- 主机**拒绝执行**，并记入审计日志。

规则完全由用户创建、编辑、删除，主机不做任何“替你决定”的内置黑名单。

---

## 2. 在哪里配置

右侧栏「设备运维」标签下，新增 **执行策略** 分页（与「设备管理 / 终端 / 日志」并列）。

- 点击右上角 **「+ 新增策略」** 打开弹窗；
- 列表里每条策略可**编辑 / 删除 / 一键启停**；
- 所有改动即时保存到磁盘（`hillstone/policies.json`，与 `devices.json` 同目录、同一加密密钥）。

---

## 3. 一条策略由什么组成

| 字段 | 含义 | 说明 |
| --- | --- | --- |
| 策略名称 | 展示用 | 例如「夜间冻结高危命令」 |
| 启用 | 开关 | 停用后该条规则整条失效，但仍保留在列表里 |
| 开始时间 | 下拉，`HH:MM` | 步进 15 分钟；留空 = 不限下界；支持跨午夜（如 `22:00`–`06:00`） |
| 结束时间 | 下拉，`HH:MM` | 步进 15 分钟；留空 = 不限上界（即到当天结束） |
| 命令模式 | 每行一个 | **词边界包含**匹配（见 §4） |
| 备注 | 可选 | 列表里展示，方便回忆规则的意图 |

> 时区固定 `Asia/Shanghai`，界面上不再提供输入框。宿主的 `window.timezone` 仍然生效，所以用 HTTP 直接写过的其它时区策略照常按原时区判断。

### 时间窗口语义

- **窗口为空**（开始、结束都不选） = **始终生效**。
- **窗口非空** = 一个**每天循环**的窗口；判断“当前时刻是否落在窗口内”以 `Asia/Shanghai` 为准：
  - 常规窗口（开始 ≤ 结束，如 `09:00`–`18:00`）：命中区间。
  - 跨午夜窗口（开始 > 结束，如 `22:00`–`06:00`）：命中“当晚 22:00 到次日 06:00”。
- 只支持“每天循环”，**不支持**按星期几、按具体日期。设计上刻意保持简单——绝大多数“冻结窗口”都是日级的。

> 列表卡片里窗口会显示成「每日 22:00–06:00」或「始终生效」，仅展示、不带时区细节。

---

## 4. 命令是怎么被匹配的

匹配规则：**词边界包含（word-boundary contains），大小写不敏感**。

- 模式 `reload` 会命中 `reload`、`reload force`、`RELOAD now`；
- **不会**命中 `reloading`、`firereload`（因为它们不是独立的“词”，前后没有词边界）。

实现上等价于：把命令按空白拆词，对每个词做 `word.toLowerCase().includes(pattern.toLowerCase())`，并且要求模式本身也出现在某个词的边界之内（即“词边界”约束）。这样 `reload` 能拦 `reload force`，但放过 `reloading` / `unreloadable`。

- **每行一个模式**；
- **多条策略之间“叠加”**：只要任意一条**已启用**的策略在当前时间命中，命令就被拒绝；
- 命中后返回结果里带 `blocked: true` 与 `blockReason`，**不会真的下发到设备**。

---

## 5. 哪些执行入口会被拦

| 入口 | 是否拦截 | 说明 |
| --- | --- | --- |
| `hillstone_run_and_analyze`（agent 工具） | ✅ 拦截 | 每条命令在执行前都过一遍策略 |
| `hillstone_send_input`（agent 工具，发到已打开终端） | ✅ 拦截 | 仅拦截**即将提交的那一行**（带 `\r` 的整行）；命中则**不写入 pty**，返回 `{ ok:false, error:'策略拒绝：…' }` |
| 人类操作员在「终端」页手敲命令（HTTP `/conn/input`） | ❌ 不拦 | 这是策略作者本人操作界面，避免“自己把自己锁死” |

设计取舍：策略的目标是约束 **agent / 自动化** 的执行，而不是限制**写规则的人**自己。因此人在终端页直接敲的命令不受影响。

---

## 6. 被拦了会怎样（审计）

每当一条命令因策略被拒绝：

1. 主机打印 `console.warn`（带策略名、命中的模式、命令）；
2. 若该连接存在会话日志（`SessionLogWriter`），写入一条 `event` 类型审计记录（设备零影响，best-effort，绝不抛错）；
3. 调用方拿到的 `CommandResult` / 工具返回里明确标注 `blocked` 与原因，便于上层（agent / UI）理解和转述。

---

## 7. 存储与接口

- 落盘文件：`hillstone/policies.json`，与设备配置同目录、同一密钥加密，结构为 `id -> ExecPolicy` 的映射。
- HTTP CRUD（均走 `/ops-api`，需要访问令牌）：
  - `GET    /ops-api/policies`       列出全部策略
  - `POST   /ops-api/policies`       新建（服务端分配 `id`、写入 `createdAt/updatedAt`）
  - `PUT    /ops-api/policies/:id`   更新（刷新 `updatedAt`；可只传要改的字段）
  - `DELETE /ops-api/policies/:id`   删除

类型定义见 `src/types.ts`：`ExecPolicy`、`PolicyWindow`、`PolicyInput`。

---

## 8. 设计要点回顾（m06680 → m06703/m06704）

- **不是内置拒绝名单**：初始方案设想过主机内置高危命令黑名单 + 每日冻结窗口；用户调整后明确为“用户自建、自行填命令”的 CRUD 模型。
- **命令匹配 = 词边界包含、大小写不敏感**（非前缀、非正则）：在“够用”和“不会误伤”之间取平衡。
- **窗口 = 仅每天循环**（可跨午夜，可留空=始终）：不做星期 / 日期维度的复杂调度。
- **审计日志**：每次拒绝都留痕，但只对设备做只读旁路，不影响设备运行。
- **agent 工具数保持 9 个**：执行策略是主机内部逻辑，不是一个新工具；拦截点就在 `runCommandVisible`（run_and_analyze 与 `/analyze` 共用）和 `hillstone_send_input.execute` 顶部。
